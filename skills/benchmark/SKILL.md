# 基准与评测核验

汇报耗时、吞吐、加速比、性能回退或评测分数前，用实跑证据核对以下问题，不靠看代码猜。
快速摸底允许只跑 1 次，但必须检查第 4、7 项并注明单次运行；技术选型或结论汇报禁止单次运行。

## 1. 运行前

- 先写清准备得出的具体结论句，以下问题全部用来检验这句话。
- 读完测试脚本，确认它计时、计数和忽略的范围。
- 检查机器负载；负载高且无法清场时，交替运行对照双方并在结论里注明。

## 2. 七项核验

1. Limiter：在未计入结果的单独运行里做 profile 或看资源监控，找出瓶颈并解释为什么不能再快一倍（留意压测端先打满）。
2. Fair Tuning：双方都用生产模式、同版本数据与合理配置（如 release 构建、索引、批处理），不拿默认配置比调优实现。
3. Physical Limits：核对带宽、核数或阿姆达尔上限；超上限的数字说明测到了缓存、空跑或 bug。
4. Error Count：统计非成功响应并核验输出正确性，快速报错或超时会伪造极快或极慢数字。
5. Repeatability：每侧交替跑至少 5 次（A、B、A、B），报中位数与波动区间；差距小于波动范围视为无显著差异。
6. End-to-End Share：微基准须附带真实端到端路径耗时占比，避免把 1% 的局部提速当成整体收益。
7. Did It Run：确认工作确实发生在计时区间内，没有被惰性求值、未 await 或编译器优化跳过。

## 汇报骨架

```md
结论：更快 / 更慢 / 无显著差异 / 无法定论
数据：<指标与单位>，<运行次数>，中位数 <X>（范围 <min> 到 <max>），瓶颈：<实测瓶颈>
缺口（如有）：<未查清项或无法定论原因>
```

查不清瓶颈、存在未调优一侧或漏查第 4、7 项时，结论必须标「无法定论」并写明缺口。
