# 规划

只做规划。结构交 `/skill:arch`，实现交 `/skill:coding`。

- design-only：只产出文档，不写实现代码。
- 需求具体就往下走；不具体先问，不猜。多轮追问，单轮聚合同类前提。
- Step 2 之后不再访谈：当前对话与代码库里已有的东西足够写 spec；缺的去读代码，不问用户。
- 术语当场定：出现含糊词或与 `docs/GLOSSARY.md` 冲突时调 `/skill:docs-glossary`。

## Step 1 — 调研

只在选型未定、或结论依赖外部事实时搜。github 项目聚焦：核心痛点、架构与依赖、活跃度、取舍、open issues。

- 只认 primary source：官方文档、源码、规范、一手 API，每条结论追到拥有它的源头，二手转述不算。
- 每条声明后面跟来源：链接，或 `路径:行号`。
- 结论、依据、未决问题三段，落盘 `docs/research/主题.md`；之后只引路径，不复述。

**Completion criterion**：每个结论附可验证链接；不该搜的时候没有搜。

## Step 2 — 追问到共识

涵盖：目标与用户、MVP 范围、不做项、技术约束、验收标准、外部依赖。

每个用户决策当场落盘 `docs/decisions/D<NN>-slug.md`，一条一文件：问题、选项、选了、理由。编号取目录最大号加一，第一次用就建目录。满足 `/skill:docs-adr` 三条门槛的只写 ADR，不写 D 文件。

**Completion criterion**：需求无歧义，或用户明确表示无需追问；每条决策已落盘。

## Step 3 — 写 spec

1. 探索仓库：相关模块怎么组织、有没有相关 ADR。全程用 `docs/GLOSSARY.md` 的规范词。
2. 写「测试决定」：从 `docs/ARCHITECTURE.md` 的 seam 清单里挑本 spec 用的。没有这份文件或清单里没有，就留空，写完 spec 跑 `/skill:arch` 补这一节。
3. 按下面的模板写，落盘 `docs/specs/NNNN-slug.md`（编号取最大号加一，第一次用就建目录），补上 README 文档小节那一行。
4. 难以逆转的选型调 `/skill:docs-adr`。

### Spec 模板

```md
## 问题
用户视角要解决的问题。

## 方案
用户视角的解法。

## 用户故事
编号条目，每条「作为 <角色>，我要 <能力>，以便 <收益>」，覆盖功能的各个侧面，宁多勿少。

## 实现决定
要建或要改的模块、模块接口、架构决定、schema 变更、API 契约、具体交互。不写文件路径和代码片段，它们很快过期。例外：状态机、reducer、schema、类型形状这类散文说不清的，内联原型里决定密集的部分并注明来自原型。

非功能：性能预算（如 P95）、安全基线（如 OWASP Top 10）、兼容范围（浏览器、运行时版本）。没有就写「无」。

## 测试决定
哪些模块被测、测试写在哪个 seam、同类测试的先例。

## 不做的
明确排除在本次范围外的。

## 未决
当前没有答案、要由用户或后续调研决定的问题，每条一行。没有就删掉本节。

## 其他
```

**Completion criterion**：spec 落盘并进 README 索引；够门槛的决策有 ADR，其余明确不建。

## Step 4 — 定范围

前提：本轮 spec 与 `docs/ARCHITECTURE.md` 就绪，「测试决定」已列 seam。

一次只拆一个阶段。

读 spec 与 seam 清单，确认这一阶段交付什么、不含什么。

**Completion criterion**：阶段边界与 MVP 范围明确。

## Step 5 — 拆任务

- 每个任务是 tracer bullet：垂直切片，穿过要碰的每一层，做完能单独验证，单次会话能做完。
- 拆之前先看有没有 prefactor：先把改动变简单，再做简单的改动。
- `/skill:audit` 报告里的 `## 质量` 线索，可以在下一阶段拆成 prefactor 任务；不重开已关闭任务。
- 「验收」写成能跑的检查（命令，或输入与期望输出），不写散文。
- 每条 AC 必须能说出「什么观察能证明它为假」；说不出来就不算 AC。
- 新增行为的 AC 在任务起点必须是红的；纯重构的 AC 是既有检查保持绿。
- AC 只依赖本任务交付物，不依赖后续任务。

格式见下（阶段表不存在就建），落点按 `../_shared/docs-rules.md`。

**Completion criterion**：用户批准，每个任务单会话能做完，每条 AC 可证伪；提示从 `/skill:coding` 领第一个任务。

### 任务格式

编号补零两位、全局连续，换阶段不重启。

```markdown
# T01 加购物车

- [ ] 未开始

## 交付物

这一任务做完，用户能做什么。

## 验收

- AC1：一条能跑的检查（命令，或输入与期望输出）

## 前置

无（或 T00）
```

- 第二行的复选框就是状态，三选一：`- [ ] 未开始`、`- [~] 待审`、`- [x] 已验收`。文件名不带状态，改状态不改名。
- 「前置」即 blocked by：只领前置全部 `[x]` 的任务。

### 阶段表

`docs/todos/README.md`，一个阶段一行：

```markdown
# 任务

- MVP：T01–T04 — 能下单并支付
- 对账：T05–T08 — 每日对账可查
```

新建任务时顺手改这一行；后面的阶段先在阶段表占一行（阶段名、任务区间、目标），进入该阶段才拆任务。

### 收到 re-plan

`/skill:audit` 判 `re-plan` 时，只改任务与 AC，不改代码；改完提示用户重新跑 `/skill:audit`。

测试规则见 `../_shared/testing.md`。
