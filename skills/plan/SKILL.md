# 规划流程

按顺序产出：`docs/PLAN.md`（决策）、`docs/ARCHITECTURE.md`（架构）、`docs/TODO.md`（任务队列）。

## 硬约束
- **零代码原则**：全过程严禁编写具体实现代码。
- **职责解耦**：系统架构按业务模块划分，拒绝技术分层。
- **单源真理 (SSOT)**：每条事实仅在一处维护。`PLAN` 仅保留决策与一句话理由，契约、字段、签名与取舍归入模块 README。
- **阶段压缩**：阶段完成后，该阶段条目压回一行并附带指针。

| 文档 | 唯一职责 |
| --- | --- |
| `docs/PLAN.md` | 为什么做、技术选型、不做项、阶段划分 |
| `docs/ARCHITECTURE.md` | 模块清单（名 + 职责）、依赖方向、目录与测试约定 |
| `docs/TODO.md` | 任务清单（`- [ ]` / `- [x]`）、验收标准、验收证据指针、前置依赖 |
| 模块 README | 内部契约（签名, 异常, 字段）、用法与取舍 |

## Step 1 — 联网调研
1. 检索一手来源（官方文档、源码、Release Notes），用 `rg`/`fd` 或搜索工具辅助。
2. 聚焦：核心痛点、架构与依赖、活跃度、取舍。

**完成标准**：结论附带可验证链接，收敛至影响选型的关键问题。

## Step 2 — 追问至共识
- 遇模糊需求直接截断提问，不盲目猜测。
- 每个问题提供推荐选项及理由，单轮聚合同类前提。

**完成标准**：用户回复确认，达成共识。

## Step 3 — 编写 PLAN.md
- 每条决策一行：`决策 | 一句话理由 | 详细出处指针`。仅分歧点展开段落。

**完成标准**：`docs/PLAN.md` 写入完毕并获批。

## Step 4 — 编写 ARCHITECTURE.md
- 声明模块表、依赖方向、代码放置规则。闭环检查：`PLAN` 中 MVP 均有模块承接。

**完成标准**：`docs/ARCHITECTURE.md` 写入完毕。

## Step 5 — 编写 TODO.md
- 拆解任务：按开发顺序将 `PLAN` 的阶段拆分为单次会话可完成的原子任务。
- 任务格式：
  ```markdown
  - [ ] T1 任务标题
    - 交付物：…
    - 验收：…
    - 验收证据：（测试文件 / 命令输出 / commit）
    - 前置：无
