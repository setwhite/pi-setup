# Style
- 使用自然、地道、简洁的中文
- 优先引用原文而非转述，且必须给出处；提出观点必须附上例子或代码
- 代码注释、docstring、设计文档、commit message 用中文；专业术语可以用英文

# KISS
按顺序选择足够解决问题的方案：
1. 提问：需求不明或存在取舍时，先问用户；用户确认前禁止开始实现
2. 不写代码：如果现有行为、配置、命令或手动操作已足够
3. 复用：删除旧代码或复用已有实现
4. 原生：优先平台、框架、标准库、现有依赖
5. 精准修改：只写当前需求所需的最少代码
6. 新抽象/子系统：只有多个当前需求明确需要时，才引入
7. 优化架构：架构导致了冗余，先改架构再实现

# Confirmation
执行前先说明做什么、影响范围，等用户明确同意；禁止未经同意就执行
- git 写操作：commit、push、建分支、改写 git 历史（amend / rebase / reset --hard）
- 新增生产依赖、改数据库 schema / migration、改 CI 配置
- 批量删除、覆盖非本会话生成的文件

# Tooling
- Python：用 uv（装依赖 `uv add`，跑脚本 `uv run python xxx.py`）；禁止 pip、直接运行 python
- Python：lint 用 ruff，类型检查用 basedpyright
- Shell：用 bash；禁止 powershell、cmd
- Node：用 pnpm；禁止 npm、yarn
- 搜索：查内容用 `rg`，查文件名用 `fd`；禁止 grep、find
- GitHub：PR / Issue 一律用 `gh` CLI
- 时间：需要当前时间先执行 `date`

# Engineering
- 动手前先搜索现成实现，有则复用；禁止手写成熟库的实现
- 修复根因；禁止特例绕过、静默吞异常、临时补丁
- 只实现当前需求；禁止兼容、过渡、双实现，除非用户明确要求
- 复杂度封装在组件内部；对外只暴露必要的生命周期与 API
- 测试只覆盖用户要求、已有契约和高风险逻辑
- 禁止过度拆分和过多测试，拆分任务前，先做开发和单元测试，安全/回归测试都放在最后统一做
- 连续三次失败后，停止，并说明位置、原因和修复方法

# Output
- 代码、代码注释、docstring、文档直接给完整可用的最终版；禁止带上修改说明、补丁说明、版本号
- 文档只写索引与事实；同一信息只写一处；禁止用文字复述代码逻辑
